# F78 — stability under concurrent use

Implemented on 2026-10-04, against the audited base commit `b35070f`.
The official need is **Expert, 1600 XP** (wave 15). The implementation effort
for this project's targeted changes is medium; this is distinct from the
competition's classification.

## Changes and essential behavior

- Incident consoles filter their own unit in SQL and select only board fields.
  Maintenance still includes cleanliness. All unit incidents, including critical
  incidents and history categories accessible through filters, remain reachable.
- Visible consoles retain the five-second interval. Hidden/offline consoles skip
  requests; React transitions prevent another refresh while one is pending.
  Returning to visibility or connectivity triggers a refresh.
- A citizen detail reads only the requested category and applies ownership in
  the database query. All timeline events and descriptions remain available.
  The complete feed and downloadable recap keep their complete history.
- Public services and announcement summaries use Next 14's persistent data
  cache, with 60-second time revalidation and explicit mutation tag invalidation.
  Cold concurrent reads are coalesced within each process. Cache hits restore
  Dates after JSON deserialization. Authenticated/private data is not cached.
- The landing page queries four services and two announcement summaries.
  Summaries omit announcement bodies; detail pages keep the full body.
  Service recommendations query three rows. Metadata and content share a
  request-scoped read for service/announcement details.
- New report, appointment and opinion references use the existing Prisma
  `cuid()` default instead of `count() + 1`. Existing references are unchanged;
  new references are no longer sequential numbers.
- MySQL booking transactions lock the service row before reading availability.
  Bookings for the same service serialize across application instances. Different
  services can proceed independently. No schema change or new migration is needed.
- An atomic conditional update claims each appointment reminder inside the same
  transaction as notification creation. A failed notification rolls back the claim.
- Login errors release the pending button and show a localized retry message.
  Password hashing, session checks and login throttling remain enforced.

## F73 decision

The broadcast poll remains at **five seconds**, including empty lists. It already
pauses in hidden tabs and prevents overlapping calls. The database query now
selects only the five public fields. Broadcasts are deliberately not placed in
the content cache: activation, removal and scheduled boundaries still apply on
each read. The browser also checks visibility immediately after returning.

At 100/500 visible tabs, the periodic baseline remains 20/100 action calls per
second, plus initial reads and focus events. The measurement below did not
justify delaying official announcements or introducing push infrastructure.
It does not prove that all hosting configurations can sustain this traffic.

## Measured results

Raw measurement output: [`F78-results.json`](F78-results.json).

Local MySQL 8.4, Prisma 5.22, Next 14.2.15 and Node 24.15.0. Synthetic fixture:
400 reports evenly split between security, medical, maintenance and cleanliness;
one citizen owns the reports, with long descriptions. The before scenarios use
the original query shapes against the same database and dataset. The after
scenarios execute the modified data functions. Each batch contains 100 or 500
simultaneous calls, not that many fully hydrated/logged-in browsers.

| Scenario | Calls | SQL before → after | p95 before → after |
| --- | ---: | ---: | ---: |
| Security incident board | 100 | 200 → 200 | 699 → 43 ms |
| Security incident board | 500 | 1000 → 1000 | 2897 → 165 ms |
| Citizen report detail | 100 | 600 → 200 | 656 → 13 ms |
| Citizen report detail | 500 | 3000 → 1000 | 3061 → 54 ms |
| Public services, warm cache | 100 | 100 → 0 | 8 → 1 ms |
| Public services, warm cache | 500 | 500 → 0 | 31 → 4 ms |

All these batches had zero errors. Incident reads return 100 rather than 400
rows. JSON size of returned DB objects falls from 1,690,571 to 31,517 bytes
(about 98% smaller). This is a representation-size measurement, not SQL wire
traffic or the size of the final browser response. The incident SQL count does
not decrease; the query returns substantially less data.

F73's current read, with one synthetic active broadcast: 100 calls produce 100
SQL statements, p95 9 ms; 500 calls produce 500 SQL statements, p95 40 ms.
These are data-function burst timings, excluding HTTP/Server Action overhead.

An isolated production build also served the public services API with one
synthetic service and warm cache:

| Virtual HTTP clients | Duration | Requests | Throughput | p95 | Errors |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100 | 15 s | 300 | 20/s | 6 ms | 0 |
| 500 | 15.01 s | 1501 | 100.03/s | 4 ms | 0 |

Clients were staggered and requested every five seconds, without overlapping
requests per client. Both runs returned the same response size (370 bytes).
This verifies that particular cached API path, not 500 simultaneous sign-ins,
all application pages, long-running production capacity or multi-instance hosting.
Latency figures are local observations, not production guarantees.

- Production build compiled, type-checked and generated its routes successfully.
- Sixteen Node tests passed: existing breadcrumbs, cold-read coalescing and
  recovery, concurrent report/opinion creation, competing/distinct bookings,
  reminder idempotency, unit filters, ownership and complete timelines for all

## Reproduce without installing dependencies

The committed runners require the project's existing `tsx`, Prisma and Next
packages. All integration writes are redirected to **local `nova_f78_test`**;
remote databases are refused. They delete only their own synthetic records.
The preload supplies a fixed locale outside Next and an identity fallback for
React 18's request-scoped cache; persistent-cache tests use Next's actual
incremental cache implementation. Therefore metadata memoization is validated
through the production build, not through that fallback.

Once, create an empty local `nova_f78_test` database, grant the local application
user access, and initialize it with the current schema. For example, generate
the initialization SQL without changing a schema or creating a migration:

```bash
./node_modules/.bin/prisma generate
./node_modules/.bin/prisma migrate diff --from-empty \
  --to-schema-datamodel prisma/schema.prisma --script > /tmp/nova-f78-schema.sql
```

Apply that SQL only to the empty test database. The verification in this session
used the existing local MySQL container. The application database was untouched.
The local generated Prisma client initially lagged behind the committed schema;
it was regenerated. The existing application DB also lacks some committed
schema fields/models; these tests do not synchronize that database.

```bash
npm run test:f78
npm run benchmark:f78
```

For runtime/HTTP checks, build and start a separate production instance. Avoid
the project's `npm run build` during isolated verification because it runs
migrations against the configured DB. Use the Next CLI directly, with
`DATABASE_URL` pointing to the local test DB, `NEXT_DIST_DIR=.next-f78` and
`NEXTAUTH_URL=http://localhost:3100`:

```bash
./node_modules/.bin/next build
./node_modules/.bin/next start -p 3100
```

Stop that test server before rebuilding its output. `.next-f78` keeps these
artifacts separate from an existing development server's `.next` directory.
Next's existing standalone configuration produces a warning with `next start`;
the verification used that CLI successfully. Deployment should use the normal
standalone artifact as documented by Next.

With the isolated instance running:

```bash
# Hold one dataset across both HTTP runs, waiting for the content cache to refresh.
npm run benchmark:f78 -- --http

# Additional read-only HTTP scenarios; refuses remote URLs.
node scripts/load-test.mjs http://localhost:3100/api/services --users=100 --seconds=30
node scripts/load-test.mjs http://localhost:3100/api/services --users=500 --seconds=30

# Browser checks use an already installed Chrome, with a temporary profile.
# Set CHROME_PATH if its binary is not in one of the known locations.
node --require ./scripts/f78-test-env.cjs --import tsx scripts/verify-f78-runtime.ts
```

The browser runner creates signed sessions for synthetic identities to test
protected pages. It does not benchmark password authentication. HTTP clients
do not emulate hydration or Server Actions. An optional `F78_COOKIE` supplies
one session for protected GET scenarios; never include it in measurement output.

## Remaining limits

Unit lists and complete citizen feeds still grow with history; pagination is a
separate follow-up, preserving critical items and full recap access. A very busy
booking service can queue transactions, and timeouts remain possible. Reminder
delivery is still triggered by page visits. Auth/bcrypt burst capacity and the
login-attempt cleanup path need a dedicated realistic sign-in scenario.

Coalescing works within a process; the persistent cache's sharing/invalidation
across instances depends on hosting configuration. A distributed cache, pool
tuning, extra indexes and push transport should follow production measurements,
not be prerequisites for these improvements. Use SQL statistics, HTTP logs and
CPU/memory observations alongside p50/p95/p99 on a longer, mixed-workload test
before making production-capacity claims.
